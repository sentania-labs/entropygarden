Mature surfaces:

- **`server/sim/`** — pure deterministic core. `tick(state, cfg)` is
  a pure function; PRNG seeded; immutable Pydantic state. Resources,
  pressures, population aging, mortality, reproduction, traits,
  events, modifiers all wired.
- **`server/api/`** — FastAPI REST + WebSocket. Endpoints for
  create/list/get/state/events/history/pause/resume/advance/delete,
  plus role-filtered views (`engineer`, `captain`) and decision
  window endpoints (`/window/current|history|action|policy/{role}`).
  Persists to SQLite every 100 ticks; in-memory `GameStore` runs
  the tick loop as an asyncio background task.
- **`server/sim/windows.py`** — decision window lifecycle, role
  hierarchy conflict resolution.
- **`server/sim/policy.py`** — standing orders, compliance stub
  (`compliance=1.0`).
- **Agent service** — multi-provider LLM (openrouter / openai /
  anthropic / local), role-specific prompts, decisions persisted.
- **Docker / nginx** — dev/prod compose split, nginx reverse proxy
  with self-signed cert fallback, HTTPS on `:8443`.
- **Client baseline** — React/Vite dashboard with role selector,
  tabs (ship + 3 rings), resource bars, history sparklines, event
  feed, WebSocket live updates.

## In-flight Feature Analysis

The dormant work is best read as **two coupled features** that
landed together:

### Feature A — Inter-ring movement & control
**Files:** `server/sim/migration.py`, restriction model in
`state.py`, five new ActionTypes, `apply_restriction_morale` in
the tick pipeline, ActionPanel UI.

**Done:** Settlers evaluate their own conditions and migrate
autonomously. Captain/Governor have three restriction levers
(lockdown, civil_restriction, labor_draft) each with a morale
cost. Cross-ring labor is supported (commuters work at 80%
efficiency). 11 dedicated tests pass the cases that matter
(balance, imbalance, blockades, cooldown, lift). Action UI
exposes the levers per role.

**Missing:** No KPI exposed on the client for migration flow
(net-in/net-out per ring, cumulative migrants). Restrictions show
in the API role views? — `models.py` doesn't appear to surface
`ring.restrictions` to the client (worth verifying).
`ring_delegate` actions are limited to `ration_resource +
impose_civil_restriction + lift_restriction` — but the API role
view for `ring_delegate` doesn't exist (only engineer/captain
views are implemented). So a player choosing ring_delegate
currently sees the captain-or-engineer fallback, which is wrong.

**To finish:** (1) expose `restrictions` and basic migration
counters in `RingSummary`, (2) implement `ring_delegate` (and
`governor`, `ecologist`) role views in `server/api/models.py`
mirroring the existing `EngineerView` / `CaptainView` pattern,
(3) confirm WebSocket broadcasts include the new fields.

### Feature B — Journey / propulsion / win-condition
**Files:** `server/sim/journey.py`, `JourneyState` + `Milestone`
in `state.py`, three destination presets in `initializer.py`,
`JourneySummary` in API models, journey badge in Header.

**Done:** Journey state loaded from preset, fuel and distance
both decrement each tick, fuel efficiency degrades with mean
maintenance debt, milestones fire when crossed, arrival_tick
records the win. 13 tests cover init, single-tick processing,
multi-tick integration, fuel exhaustion, no-journey backward
compat. Header shows destination + progress percent.

**Missing:** No win/loss screen in the client. No "viable
population minimum" enforcement at arrival —
`SimConfig.viable_population_minimum = 50` exists but nothing
reads it. No fuel meter or ETA on the client. No explicit
"deceleration phase" mechanic — milestones include `decel` IDs
but nothing acts on them (description text only).

**To finish:** (1) UI strip showing fuel %, fuel efficiency,
ETA, next milestone (data is already in `JourneySummary`), (2) a
terminal-state view (won / lost / pyrrhic) when `arrival_tick`
is set or fuel hits 0 with distance remaining, (3) actually
apply the `decel` milestone effect (e.g. higher base_fuel_per_tick
past it), (4) wire `viable_population_minimum` into the win
check.

### Effort to land both end-to-end
Backend is essentially done — both feature areas have green tests.
The remaining work is **client surface + missing role views**:
roughly 1-2 sessions to expose the data the sim already produces
and to implement the three missing role views in the API.
