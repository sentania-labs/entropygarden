# Architecture — Entropy Garden

## Current Implementation (Phase 2 complete)

### Service layout

```
┌─────────────────────────────────────────────────────┐
│  Docker host                                        │
│                                                     │
│  ┌─────────────────────────────────────────────┐   │
│  │  server container                           │   │
│  │                                             │   │
│  │  FastAPI (uvicorn)                          │   │
│  │  ├── api/           REST + WebSocket        │   │
│  │  ├── sim/           tick loop (asyncio bg)  │   │
│  │  └── agents/        LLM agent runner        │   │
│  │                                             │   │
│  │  :8000                                      │   │
│  └─────────────────────────────────────────────┘   │
│                                                     │
│  ┌─────────────────────────────────────────────┐   │
│  │  client container  (--profile client)       │   │
│  │  React + Vite dev server  :5173             │   │
│  └─────────────────────────────────────────────┘   │
│                                                     │
│  ${DATA_DIR}/db/entropy_garden.db  (SQLite)         │
└─────────────────────────────────────────────────────┘
```

### Key components

**`server/sim/`** — Deterministic simulation core. Pure functions: `tick(state) → state`. No I/O, no LLM. Seeded PRNG for reproducible replay. ~169 ticks/sec at 1000 population.

**`server/api/`** — FastAPI app. Owns the in-memory game state (`GameStore`). Runs the tick loop as a background `asyncio` task. Broadcasts state updates over WebSocket. Persists to SQLite every 100 ticks.

**`server/agents/`** — LLM agent service. Subscribes to the internal queue, wakes on `decision_window` messages, calls the LLM, submits actions through the normal action API. Providers: openrouter (default), openai, anthropic, local/ollama.

**`server/sim/windows.py`** — Decision window lifecycle: opens every N ticks, collects role actions, resolves conflicts by role hierarchy (captain > engineer > ecologist > governor > ring_delegate), triggers policy fallback for absent roles.

**`server/sim/policy.py`** — Standing orders per role. Compliance factor (stubbed at 1.0 for MVP, designed for future decay).

### Data model

- State is immutable Pydantic models. `tick()` returns a new `GameState`.
- Persisted as JSON to SQLite (`games`, `history`, `agent_decisions` tables).
- `window_history` and `policies` travel with `GameState` — no separate tables needed for MVP.

### Deployment (current)

```
./setup.sh            # creates DATA_DIR, writes .env
docker compose build
docker compose up     # server on :8000, --reload enabled
docker compose --profile client up   # + client on :5173
```

Bind mounts (not named volumes) so data is always at a known path on the host.

## Architectural Constraint: Stateful Tick Loop

**The sim tick loop runs inside the FastAPI process.** This is intentional for MVP simplicity but is the primary constraint on scaling.

Consequences:
- Only one server container can run at a time (two = two tick loops = diverging game state)
- SQLite is sufficient because there's only one writer
- Horizontal API scaling is not possible in the current architecture

This constraint must be resolved before deploying to Kubernetes. See [Roadmap](roadmap.md) Phase 3.

## Migration Path: Docker → Kubernetes

### Phase 2 pre-requisites (required before k8s)

Before Kubernetes is viable, the architecture needs two changes:

**1. Separate the sim engine into its own service**

The tick loop moves out of the FastAPI process into a dedicated `sim-engine` container. It writes state to PostgreSQL on every tick (or every N ticks with WAL). The API layer becomes stateless — it reads from the DB, writes actions to the DB, no in-memory game state.

```
sim-engine container     FastAPI container(s)
─────────────────        ────────────────────
tick loop                REST API (stateless)
writes → Postgres        reads ← Postgres
                         WebSocket broadcast
```

**2. Add Redis (or Postgres LISTEN/NOTIFY) for WebSocket fan-out**

Currently WebSocket broadcasts use an in-process asyncio queue. With multiple API pods, a client connected to pod A won't receive ticks generated by pod B. Redis pub/sub (or Postgres LISTEN/NOTIFY) decouples the broadcast from the process.

### Phase 3: Kubernetes topology

```
                        ┌──────────────────────────────────────────┐
                        │  Kubernetes cluster                       │
                        │                                           │
  browser ──────────▶  │  Ingress (nginx / Traefik)               │
                        │    /         → client  Deployment        │
                        │    /api      → server  Deployment        │
                        │    /ws       → server  Deployment        │
                        │                                           │
                        │  client Deployment   (N pods, stateless) │
                        │  server Deployment   (N pods, stateless) │
                        │  sim-engine StatefulSet  (1 pod)         │
                        │                                           │
                        │  PostgreSQL  StatefulSet + PVC           │
                        │    or managed (RDS, Cloud SQL, etc.)     │
                        │                                           │
                        │  Redis       StatefulSet + PVC           │
                        │    or managed (ElastiCache, etc.)        │
                        └──────────────────────────────────────────┘
```

**StatefulSet vs Deployment:**
- `sim-engine`: StatefulSet, 1 replica. Game tick is serial by design — this pod is the authoritative source of state advancement. Scaled vertically, not horizontally.
- `server` (API): Deployment, N replicas. Stateless once backed by Postgres + Redis. Scales horizontally.
- `client`: Deployment, N replicas. Pure static assets served by Vite/nginx. Scales freely.
- `postgres`, `redis`: StatefulSet with PVC (or hand off to a managed service — strongly recommended for production).

**Volumes: Docker named volumes → Kubernetes PVCs**

| Docker Compose | Kubernetes |
|----------------|------------|
| Named volume `db_data` | PersistentVolumeClaim (ReadWriteOnce for sim-engine) |
| Named volume `client_modules` | Baked into image at build time (not needed in k8s) |
| Bind mount `./server:/app/server` | Not used in prod — source is baked into image |

In k8s, `VOLUME` in a Dockerfile creates anonymous volumes — avoid it. Define PVCs in manifests, not in Dockerfiles.

**Key PVC design:**
- PostgreSQL data: `ReadWriteOnce`, 10–50Gi, backed by fast block storage
- Redis data (if persisting): `ReadWriteOnce`, 1–5Gi
- No PVC needed for sim-engine or API — they are stateless once on Postgres

### What doesn't change between Docker and k8s

- Container images are identical (no Dockerfile changes for k8s)
- Environment variables are the same (k8s Secrets/ConfigMaps replace `.env`)
- The sim engine logic, API contracts, and agent service are unchanged
- SQLite can be used for local dev forever — only the server deployment changes

## Configuration

All configuration via environment variables:

| Variable | Default | Purpose |
|----------|---------|---------|
| `ENTROPY_GARDEN_DB` | `/data/entropy_garden.db` | SQLite path (Docker) / ignored (k8s+Postgres) |
| `CORS_ORIGINS` | `http://localhost:5173` | Allowed browser origins |
| `VITE_API_URL` | `http://localhost:8000` | API URL as seen from browser |
| `AGENT_GAME_ID` | — | Game ID for the LLM agent runner |
| `AGENT_ROLE` | — | Role the agent plays (`engineer`, `captain`, etc.) |
| `LLM_PROVIDER` | `openrouter` | LLM backend: `openrouter`, `openai`, `anthropic`, `local` |
| `OPENROUTER_API_KEY` | — | API key for OpenRouter |
| `DATA_DIR` | `/var/docker/entropygarden` | Host path for bind mounts (Docker only) |
